## 0. 왜 만드나

Gazebo 기본 물리는 중력 + 로터 추력만 계산한다. 축대칭 동체의 항력·법선력·정적안정·
감쇠는 아무도 안 넣어준다. 지금 SITL 을 돌리면 **공기 없는 우주에서 나는 쿼드**다.
300 km/h(83.3 m/s)에서 동압이 4.25 kPa 이라 공력이 지배적이다.

**요구사항**: 공력 담당이 CFD/풍동 결과를 CSV 로 주면 **코드 수정 없이** 반영된다.

## 1. ⚠ 최대 위험 — 좌표계

`control/dynamics.py` 는 **z-down 동체좌표**(미사일 관례)인데 Gazebo 는 **FLU/ENU** 다.
부호가 뒤집혀도 **시뮬은 멀쩡히 돌고 결과만 조용히 틀린다.**

이 프로젝트에 이미 같은 계열 사고가 있었다 — 쿼터니언이 scalar-last 인데 트림 w 가
전 속도에서 정확히 0 이라, `q_w>0` 정규화가 롤 부호를 통째로 뒤집었다.
그때도 시뮬은 멀쩡히 돌았다.

그래서 **검증(§4)을 구현(§3)보다 먼저 설계했다.**

## 2. 좌표계 계약

### 2.1 프레임 3개

| 기호 | 이름 | 정의 | 누가 쓰나 |
|---|---|---|---|
| `W` | 월드 | Gazebo ENU (x=동, y=북, z=상) | gz 가 힘을 받는 곳 |
| `L` | 링크 | Gazebo 링크 프레임, FLU 관례 (x=앞, y=좌, z=상) | SDF 가 관성·로터를 적는 곳 |
| `B` | 동체(미사일) | **x=기수, y=우현, z=아래** (FRD) | `dynamics.py`·팀 `aero.py` 수식이 사는 곳 |

### 2.2 L → B 변환은 **SDF 파라미터**로 명시한다

```xml
<nose>1 0 0</nose>      <!-- B 의 +x (기수)를 L 성분으로 -->
<right>0 -1 0</right>   <!-- B 의 +y (우현)를 L 성분으로 -->
```

세 번째 축은 오른손계로 **유도**한다 (사람이 적으면 틀린다):

```
down = nose × right          (FRD 에서 앞 × 우 = 아래)
R_LB = [ nose | right | down ]   (열벡터 3개)
```

- 벡터 L→B : `v_B = R_LBᵀ · v_L`
- 벡터 B→L : `F_L = R_LB · F_B`

**기본값** `nose=(1,0,0)`, `right=(0,-1,0)` → `down=(0,0,-1)` → `R_LB = diag(1,-1,-1)`.
이게 x축 180° 회전, 즉 FLU↔FRD 표준 변환이다.

**테일시터라 기수를 링크 +z 로 두고 싶으면** `nose=(0,0,1)`, `right=(0,-1,0)` 으로
바꾸면 끝이다 — **C++ 수정 없음**. (실제 값은 §7 미결 항목에서 확정)

### 2.3 왜 굳이 B 를 거치나 — 네이티브 FLU 로 안 쓰는 이유

C++ 한 줄 한 줄이 `dynamics.py` 한 줄 한 줄과 **눈으로 대조**되게 하려고.
FLU 로 새로 유도하면 그 유도 과정 자체가 검증 대상이 되어 부호 사고가 날 자리가
오히려 늘어난다. 변환은 2줄이고, 단위테스트로 못 박는다.

### 2.4 모멘트도 **같은** 변환을 쓴다

모멘트는 유사벡터(pseudovector)라 **반사(det=−1)에서는** 벡터와 다르게 변환된다.
`R_LB` 가 진짜 회전(det=+1)이면 벡터와 동일하다.

→ 그래서 플러그인은 `Configure()` 에서 **직교성과 det≈+1 을 검사하고, 아니면
   에러 로그를 내고 힘을 하나도 걸지 않는다.** 조용히 틀리는 걸 막는 유일한 방법이다.

검사 항목:
- `‖nose‖ ≈ 1`, `‖right‖ ≈ 1` (아니면 정규화하고 경고)
- `|nose · right| < 1e-6` (직교)
- `det(R_LB) > 0.999` (오른손계)

### 2.5 대기속도

```
v_air_W = v_link_W − v_wind_W          (바람은 월드 ENU 로 받는다)
v_L     = R_WLᵀ · v_air_W
v_B     = R_LBᵀ · v_L
ω_L     = R_WLᵀ · ω_link_W
ω_B     = R_LBᵀ · ω_L
```

힘·모멘트는 링크의 **질량중심(CoM)** 에 건다. `x_cp` 가 CG 기준이므로 SDF 의
`<inertial><pose>` 가 실제 CG 를 정확히 담고 있어야 한다 (§7).

## 3. 공력 모델 — 두 소스가 **같은 수식**임을 확인했다

`_body_aerodynamics()` 와 팀 `modules/aero.py` 를 대조한 결과 (검증 스크립트:
`tools/crosscheck_aero.py`), **4개 속도 × 8개 받음각에서 최대 상대오차 2.7e-10**:

| `dynamics.py` 슬롯 | 팀 `aero.py` 대응 | 항등식 |
|---|---|---|
| `C_Na` | `CN_alpha` | q̄S·CN_α·sinα·cosα ≡ ½ρS·C_Na·u_b·V_cf |
| `C_dc` | `eta_cf · Cd_c · A_plan / S_ref` | q̄S·(…)·sin²α ≡ ½ρS·C_dc·V_cf² |
| `C_A0` | `CD0(V)` | 축력이 α 무관 |
| `C_Aa2` | (없음) → `0` | |

> ⚠ 이 대조에서 **플레이스홀더 `C_dc = 1.2` 가 스케일 누락**임이 드러났다.
> 주석은 "원통 표준"인데 그 슬롯이 요구하는 건 `η·Cd_c·(A_plan/S_ref)` 다.
> 플레이스홀더 형상으로는 **≈ 5.6** 이어야 한다 (약 4.7배 과소).
> α=7.5°(순항)에선 C_N 의 2.6%→12% 로 작지만, **α=30°(고속 틸트)에선 C_N 2.90→4.01
> (+38%)**. 파이썬 시뮬이 고속을 낙관적으로 본다. 시뮬 결과가 바뀌는 수정이라 보류.

**따라서 CSV 스키마 하나로 두 소스를 다 담을 수 있다.**

### 3.1 계산식 (B 프레임, `dynamics.py` 와 한 줄씩 대응)

```
V_sq  = u² + v² + w² + ε
V     = √V_sq
V_cf  = √(v² + w² + ε)             크로스플로 속도
q̄     = ½ ρ V_sq
α     = atan2(V_cf, u)             전 받음각 ∈ [0, π]

축력    F_x = −q̄ · S_ref · C_A(V, α)
법선력  |F_N| = q̄ · S_ref · C_N(V, α)
        방향 = −(0, v, w)/V_cf     (크로스플로 반대 방향)
        → F_y = −|F_N|·v/V_cf ,  F_z = −|F_N|·w/V_cf

정적모멘트  M = r_cp × F_N,  r_cp = (x_cp, 0, 0)
        M_x = 0
        M_y = −x_cp · F_z
        M_z = +x_cp · F_y

감쇠모멘트  df = ¼ ρ V S_ref d_ref²
        M_x += df · C_lp · p
        M_y += df · C_mq · q
        M_z += df · C_mq · r        (축대칭 → C_nr = C_mq)
```

`V_cf → 0` 특이점은 `dynamics.py` 처럼 분모를 소거해 피한다:
`F_N_over_Vcf = q̄·S_ref·C_N/V_cf` 를 직접 만들지 말고, **표를 `C_N/sinα` 로 저장**하지
않고 `C_N` 그대로 저장한 뒤 `|F_N|/V_cf = q̄·S·C_N/V_cf` 를 계산할 때
`V_cf < ε` 이면 법선력을 0 으로 둔다 (α=0 에서 C_N=0 이므로 물리적으로 맞다).

## 4. 검증 설계 — **2겹으로 나눈다**

하나로 묶으면 실패했을 때 원인이 "수식"인지 "프레임"인지 못 가린다.

### 겹 1 — 수식 이식 검증 (gz 불필요, macOS 에서도 빌드/실행 가능)

- 공력 코어를 `include/fast_drone/aero_core.hpp` **하나로 분리**. gz 헤더 의존 0.
- 파이썬이 `test/aero_reference.csv` 생성 — 상태 N개 `(u,v,w,p,q,r)` → `(Fx..Mz)`
  **전부 B 프레임**.
- `test/test_aero_core.cc` 가 같은 상태를 코어에 넣고 대조.

**두 갈래로 나눠 잰다:**

| 테스트 | 평가점 | 기준 | 무엇을 재나 |
|---|---|---|---|
| A. 수식 이식 | **격자점 위** | 상대오차 < 1e-9 | 이식이 정확한가 (보간오차 0) |
| B. 보간 품질 | 격자 사이 | 상대오차 보고 (목표 < 1%) | 격자가 충분히 촘촘한가 |

A 와 B 를 섞으면 "1% 안에 들어왔으니 됐다"로 부호 사고를 놓친다.

**상태 설계가 핵심**: `u,v,w,p,q,r` 이 전부 0 이 아니고 **서로 다른 값**이어야
y↔z 뒤바뀜이 드러난다. 대칭 상태(v=0, p=0)만 쓰면 부호 사고가 그냥 통과한다.

필수 케이스:
1. 완전 비대칭 (6성분 전부 서로 다른 0 아닌 값) ← **부호 사고 검출기**
2. 순수 축류 (v=w=0) — α=0 특이점
3. 순수 크로스플로 (u=0) — α=90°
4. 역류 (u<0) — α>90°
5. 순수 롤 / 순수 피치 / 순수 요 (각각 하나만 0 아님) — 감쇠 축 분리
6. 정지 (전부 0) — 0/0 특이점
7. 순항 트림 근방 (83.3 m/s, α≈트림값)
8. y↔z 교환쌍: `(u, a, b, …)` 와 `(u, b, a, …)` — 축대칭이면 크기가 같아야 한다

### 겹 0 — 물리 상식 검사 (플러그인이 스스로 확인, CSV 로드 직후 1회)

CSV 가 이상해도 잡는다. 실패 시 **에러 로그 + 힘 미적용**.

1. `α=0` 에서 `C_N = 0`
2. `C_A > 0` (모든 격자점)
3. `C_lp < 0`, `C_mq < 0` (감쇠는 항상 ω 를 줄이는 방향)
4. 격자가 단조 증가 (V, α 둘 다)
5. `x_cp` 가 동체 길이 범위 안

```
./gz_aero/verify.sh          # 표 생성 -> 기준값 생성 -> 빌드 -> 대조
```

| 항목 | sized | placeholder |
|---|---|---|
| 검사 수 | **146 / 146 통과** | **146 / 146 통과** |
| test A 최대 상대오차 (격자점 위) | ~1e-13, 다수 정확히 0 | ~1e-10 |
| test B 최대 힘 오차 (칸 중점 3320점) | 0.0249 N (무게의 0.15%) | 0.0186 N |
| test B 최대 모멘트 오차 | 1.62e-3 N·m | 1.65e-3 N·m |

**허용오차의 바닥은 정체가 밝혀진 것이다** — 모르는 채로 느슨하게 잡은 값이 아니다:

1. 파이썬 원본은 `V_cf = sqrt(v²+w²+EPS)` 로 0 나눗셈을 피한다. C++ 은 **각도
   계산에서만** 그 EPS 를 뺐다 — 안 빼면 `α=0` 에서 `atan2(1e-4, u) = 1.2e-6 rad`
   이 되어 표의 0 행이 아니라 그 옆을 섞어 읽는다 (placeholder 에서 1e-7 오차로
   실측됨). 대신 크로스플로 항에 `C_dc·EPS/(2·V_cf)` 가 남는다 — V=5 m/s 에서 2e-10.
2. `q̄` 와 감쇠가 쓰는 `V_sq` 는 원본의 EPS 를 그대로 뒀다. 그쪽 차이는 0 이다.
3. `V=0` 케이스는 힘 자체가 1e-11 N 이라 절대 허용오차(1e-11 N)가 흡수한다.

부호 반전·축 뒤바뀜·계수 오배치 같은 **진짜 이식 오류는 전부 O(1)** 이므로
1e-9 허용치로 무조건 걸린다.

### 4.5 격자를 사람이 안 찍는 이유

`gen_aero_csv.py` 의 `adaptive_v_grid` / `adaptive_alpha_grid` 가 격자를 정한다.
기준은 계수 오차가 아니라 **힘 오차**(`F_TOL_N = 0.02 N`, 기체 무게의 0.12%)다.

이게 중요한 이유: 계수 기준으로 쪼개면 저속에 점이 몰린다 (CD0(V) 가 레이놀즈수
의존이라 가파르다). 그런데 V=1.5 m/s 에서 `ΔC_A = 1e-3` 이 만드는 힘은 9e-6 N —
비행에 아무 영향이 없다. 반대로 고속 고받음각에서는 `ΔC_N = 7e-3` 이 0.35 N
(무게의 2.2%) 을 만든다. **"계수가 얼마나 틀렸나"가 아니라 "그게 힘으로 얼마가
되나"로 쪼개야 한다.**

균일 α 2.5° 로 시작했을 때 힘 오차가 0.352 N 이었고, 힘 기준 적응격자로 바꾸니
**0.0249 N** 이 됐다 (V 격자는 오히려 48점 → 11점으로 **줄었다**).

## 5. CSV 스키마

```
# fast_drone aero table v1
# frame: body FRD (x=nose, y=right, z=down)
# S_ref: 0.00636173      <- 있으면 플러그인이 SDF 값과 대조, 0.1% 넘게 다르면 에러
# d_ref: 0.09
# source: rocket-drone/modules/aero.py @ d_body=0.09 lambda=8.0 S_fin=0.022 x_fin=0.60
V_mps,alpha_rad,C_A,C_N,x_cp,C_lp,C_mq
0.0,0.0,0.443,0.0,-0.0998,-5.0,-10.0
...
```

- **정규 격자**(rectilinear): V 값 목록 × α 값 목록의 모든 조합. 순서는 V 바깥, α 안쪽.
- `C_A`, `C_N` : `S_ref` 기준 무차원
- `x_cp` : **CG 기준 body x [m]**, 음수 = CG 뒤 = 정적 안정
  (팀 `aero.py` 는 기수 기준 양수이므로 `x_cp_body = −(x_cp_nose − x_cg)` 로 변환해 넣는다)
- `C_lp`, `C_mq` : 감쇠 미분계수. 팀 모델엔 없으므로 당분간 상수.
- α 범위는 `[0, π]` 만 담는다. **음의 α 는 축대칭성으로 유도**한다
  (법선력 방향이 크로스플로 벡터로 결정되므로 부호가 자동으로 맞는다).

### 5.1 무엇이 어디 사나

| 항목 | 사는 곳 | 이유 |
|---|---|---|
| `C_A, C_N, x_cp, C_lp, C_mq` 격자 | **CSV** | 공력 담당이 주는 것 |
| `S_ref, d_ref` | **SDF** (+CSV 주석에 사본, 불일치 시 에러) | 기체 형상. 한쪽만 바뀌면 전체가 조용히 스케일된다 |
| `rho` | **SDF** | 환경 |
| `nose, right` | **SDF** | 모델 배치 |
| `link_name`, `csv_file` | **SDF** | 배선 |

### 5.2 축대칭 가정 — 무엇을 쓰고 있고, 어디가 확장점인가

이 v1 은 **완전 축대칭**을 가정한다. 별도 연구에서 축대칭을 일반화하고 있으므로,
가정을 암묵적으로 두지 않고 **CSV 첫 줄에 선언하고 플러그인이 검사**한다:

```
# schema: axisym_v1
```

플러그인은 이 줄이 없거나 다르면 **에러를 내고 힘을 걸지 않는다.** 일반화 연구가
만든 `asym_v2` 표를 v1 플러그인이 조용히 읽어 절반만 맞는 힘을 내는 사고를 막는다.

**축대칭이 실제로 쓰이는 곳 4군데** (일반화 시 여기가 전부 바뀐다):

| # | 위치 | 축대칭이라서 되는 것 | 일반화하면 |
|---|---|---|---|
| 1 | 표의 축 | 계수가 `(V, α)` 만의 함수 | `(V, α, φ)` — φ = 공력 롤각. 핀 4매는 90° 주기 |
| 2 | 법선력 방향 | `F_N ∥ −(0,v,w)` — 크로스플로 평면 안 | 면외 측력이 생겨 `C_Y`·`C_Z` 를 따로 둬야 함 |
| 3 | 감쇠 | `C_mq = C_nr` (한 계수로 y·z 공용) | 두 계수 분리 |
| 4 | 롤 모멘트 | 공력 롤 모멘트 = 감쇠뿐 (`C_lp·p`) | 유도 롤 모멘트 `C_l(α, φ)` 추가 |

**확장 방식** (v2 를 만들 때 v1 을 안 깨는 길): 표에 `phi_rad` 축을 **추가**하고
`# schema: asym_v2` 로 선언한다. φ 값이 하나뿐인 표는 수치적으로 v1 과 동일하므로,
v2 플러그인은 v1 표도 읽을 수 있다 (반대는 막힌다 — 그게 의도다).

## 7. 미결 항목 (확정되면 여기 갱신)

- [ ] **`fast_missile_base/model.sdf` 확보** — 저장소 밖(Ubuntu PX4 트리)에 있다.
      링크·관성·비주얼을 봐야 §2.2 의 `nose`/`right` 실제 값을 확정할 수 있다.
- [ ] **테일시터 링크 축 확정** — 로터 추력축이 장축이므로, PX4 멀티콥터 믹서가
      가정하는 "추력 = 링크 +z(FLU)" 와 맞추면 **기수 = 링크 +z** 가 된다.
      그러면 `nose=(0,0,1)`. PX4 tailsitter 자세 규약 확인 후 확정.
- [ ] **비주얼과 물리의 장축 불일치** — HANDOFF:145 는 비주얼이 "세로 미사일 동체",
      물리는 `Ixx=0.02`(장축=body x). 눈으로 하는 첫 검증이 막히므로 정합 필요.
- [ ] **`C_dc` 스케일 누락 수정 여부** (§3 경고) — 파이썬 시뮬 결과가 바뀐다.
- [ ] **α > 90° 역류에서 축력 부호** — ⚠ **실측으로 확인한 모델 한계**.
      `dynamics.py` 의 `Fx = −q̄·S·C_A` 는 `q̄ > 0`, `C_A > 0` 이라 **α 와 무관하게 항상 −x**다.
      즉 꼬리부터 들어오는 흐름(α=180°)에서도 힘이 뒤로 밀어 **음의 감쇠**가 된다.
      멀티로터는 늘 기수 전방이라 이 영역을 안 지났지만, **테일시터는 호버 강하·천이에서
      routine 하게 지난다.** α=90° 에서도 축력이 −2.95 N (0 이어야 함) 나온다.
      → 표가 `C_A(α)` 를 담으므로 **코드 수정 없이 표로 고칠 수 있다** (α>90° 에서 음수 C_A).
        다만 올바른 값은 CFD/풍동이 줘야 한다. 공력 담당에게 요청할 항목.
      → 그때까지 플러그인은 §4 겹0 검사에서 **경고를 낸다**(조용히 넘어가지 않는다).
- [ ] **감쇠계수 출처** — 팀 `aero.py` 에 없다. 당분간 `dynamics.py` 값
      (`C_lp=−5`, `C_mq=−10`) 을 쓰되 d_ref 가 0.15→0.09 로 바뀐 영향 확인 필요.
