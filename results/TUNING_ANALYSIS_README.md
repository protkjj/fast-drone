# 튜닝 기록 분석 도구 (`control/tuning_analysis.py`)

> **가설 단계 도구다. 이 도구의 출력으로 결론을 내리지 않는다.**
> 제어기 간 우열, "튜닝이 쉬운 구조" 같은 주장은 이 표·그림만으로 성립하지 않는다(아래 "해석 주의사항").
> 출력 라벨은 튜닝 기록의 라벨(`PILOT`)을 그대로 따르거나, 미완료 기록을 잘라 쓴 경우 `PARTIAL`이다.

## 무엇을 하나

`control/arena_tune.py`가 남긴 튜닝 기록을 **읽기만** 해서(형식을 바꾸지 않는다) 제어기별로 다음을 만든다.

| 항목 | 출처 |
|---|---|
| 첫 평가(사전값 = 기본 가중치) 목적함수, 실패 여부, 실패한 튜닝 시나리오 | `<제어기>.jsonl` 0번 줄 |
| 학습 곡선(평가 k회까지의 누적 최선 값) | `<제어기>.jsonl` 전체 |
| 90% 도달 평가 횟수 — 정의 A·B·C, 첫 비실패 평가 횟수 | 위 곡선 |
| 튜닝 파라미터 개수 | `configs/arena.json` → `tuning.parameters` (record의 `parameter_names`와 대조) |
| GSLQR 운용점 개수 | `configs/arena.json` → `controllers.GSLQR.V_table_m_s`의 길이 |
| ×0.5·×2 민감도 실험 **실행 계획** (실행하지 않음) | record의 `best_values`·`best_exponents` |

시뮬레이션은 한 번도 돌리지 않는다. 입력은 JSON 파일뿐이다.

## 사용법

```bash
# 완료된 튜닝(모든 제어기가 예산을 다 씀) — 기본(엄격) 모드
python3 -m control.tuning_analysis --run-dir results/arena/tuning/pilot24

# 튜닝이 아직 진행 중일 때 중간 점검 — 가장 짧은 평가 수로 모두 잘라 PARTIAL로 표시
python3 -m control.tuning_analysis --run-dir results/arena/tuning/pilot24 --truncate-to-common

# 출력 위치 지정(기본: <run-dir>/analysis)
python3 -m control.tuning_analysis --run-dir <dir> --out-dir <out>

# 테스트(합성 기록만, 1~2초)
python3 -m pytest control/test_tuning_analysis.py -q
```

종료 코드: 성공 0, 분석 거부 2(`REFUSED: <사유>` 출력).

### 출력 파일

| 파일 | 내용 |
|---|---|
| `summary.md`, `summary.csv` | 제어기별 표(열 정의는 아래) |
| `analysis.json` | 표 + 평가별 목적함수·실패 여부·누적 최선 곡선(원자료) |
| `learning_curves.png` | 제어기별 패널. 누적 최선 계단선, 평가 원값(실패는 ×), A(○)·B(□)·C(△) 도달 지점, 실패 벌점 수준(점선). y축 로그·전 패널 공유 |
| `sensitivity_plan.json` | 민감도 실험 실행 계획. **엄격 모드에서만** 쓴다(PARTIAL엔 "최종 가중치"가 아직 없어서) |

## 분석 거부 규칙 (I-4와 같은 원칙)

| 상황 | 기본 모드 | `--truncate-to-common` |
|---|---|---|
| 제어기 간 `budget`이 다름 | 거부 | **거부** (예산이 다르면 탐색 보폭 재시작 시점부터 달라져 잘라도 같은 조건이 아니다) |
| record의 `spent` ≠ JSONL 줄 수, JSONL 인덱스 빈틈·중복 | 거부 | 거부 |
| 미완료(`status≠complete`, `spent<budget`) | 거부 | 허용 — 모두 공통 최소치로 자르고 `PARTIAL` |
| I-4의 나머지(튜닝이 본시험 시나리오 사용, 난수 범위 겹침, 목적함수·탐색 설정·시나리오 목록 불일치) | 거부 | 거부 |
| record 요약과 JSONL이 어긋남(첫 목적함수 ≠ `prior_objective`, 최소 ≠ `best_objective`, 0번 평가가 사전값이 아님) | 거부 | 거부 |
| record의 `parameter_names` ≠ 현재 `configs/arena.json` | 거부 | 거부 |
| record의 `config_sha256` ≠ 현재 설정 | **경고만** (설명 문구 수정만으로도 해시가 바뀌므로) | 경고만 |

I-4 판정은 `control/arena_tune.check_tuning_records`를 그대로 호출한다(규칙을 복사하지 않음 — 두 벌이 되면 언젠가 어긋난다).

## 표의 열

| 열 | 뜻 |
|---|---|
| `evals` | 분석한 평가 횟수(엄격 모드면 = 예산) |
| `n_params` | 튜닝 파라미터 개수 |
| `gslqr_op_points` | GSLQR 게인 스케줄 운용점 개수(설정값). GSLQR 외 제어기는 `—` |
| `first_obj`, `first_failed`, `first_failed_scenarios` | 사전값(기본 가중치) 평가 결과 |
| `best_obj`, `best_at` | 최선 목적함수와 그 값을 **처음** 얻은 평가 번호 |
| `n_failed_evals` | 실패 시나리오가 하나라도 있었던 평가 수 |
| `first_nonfailed` | 모든 튜닝 시나리오를 실패 없이 통과한 첫 평가 번호 |
| `to90_A_improve` | 정의 A 도달 평가 번호 |
| `to90_B_ratio` | 정의 B 도달 평가 번호 |
| `to90_C_improve_nonfailed` | 정의 C 도달 평가 번호 |

평가 번호는 1부터 센다. 도달하지 못하면 `—`.
**캐시 적중도 평가 1회로 센다** — arena_tune이 예산을 그렇게 계상하기 때문이다(재방문도 예산을 쓴다). 캐시 적중 줄은 `scenarios`가 비어 있어 실패 여부를 같은 좌표의 첫 실제 평가에서 가져온다.

## "최선 값의 90%" — 세 가지 정의

목적함수 f는 **작을수록 좋다**(`window_rmse_velocity + window_rmse_z`, 시나리오 실패 시 그 시나리오 점수가 1000, 튜닝 시나리오 5개 평균).
그래서 "최선 값의 90%"를 글자 그대로 `0.9·f*`로 읽으면 f*보다 작은 값이라 영원히 도달하지 못한다. 아래 세 정의를 모두 계산한다(f₀ = 첫 평가, f* = 최선, 곡선 = 누적 최선).

| 정의 | 임계값 | 유리하게(빨리) 나오는 경우 | 불리하게(늦게) 나오는 경우 |
|---|---|---|---|
| **A** 개선폭 90% | f ≤ f₀ − 0.9(f₀ − f*) | **첫 평가가 실패한 제어기.** 벌점 1000에서 빠져나오는 것만으로 개선폭 대부분을 채워(f*≈3이면 99% 이상), 실패 탈출 직후를 "90% 도달"로 찍는다. 사전값이 이미 최선이면(f₀=f*) 1회째에 도달한 것으로 나온다 | 사전값이 이미 좋아 개선폭이 작은 제어기. 남은 개선이 잡음 수준이라 90% 지점이 사실상 우연히 정해진다 |
| **B** 비율 | f ≤ f*/0.9 (최선보다 약 11% 나쁜 수준 이내) | **최종 목적함수가 큰(성능이 나쁜) 제어기** — 허용 폭 0.11·f*가 절대값으로 넓다. 사전값이 최선의 11% 이내이면 1회째 | 최종 목적함수가 작은(좋은) 제어기 — 허용 폭이 절대값으로 좁다. 실패 여부에는 휘둘리지 않는다 |
| **C** 개선폭 90%, 기준을 첫 비실패로 | f ≤ f_nf − 0.9(f_nf − f*), 첫 비실패 평가부터 셈 | 첫 비실패 평가가 우연히 최선에 가까운 제어기(남은 개선폭이 작아 금방 도달) | 첫 비실패 평가가 "겨우 통과"(오차 큼)인 제어기 — A와 비슷하게 긴 꼬리를 센다. 실패를 한 번도 안 한 제어기는 **C = A** |

그리고 `first_nonfailed`(첫 비실패 평가 횟수)는 **실패 탈출**만 따로 센다. A가 작고 C가 크면 "빨리 수렴"이 아니라 "실패 탈출이 개선폭 대부분"이라는 뜻이다. 합성 예시(시드 고정, 첫 두 평가 실패)에서 A=3·C=17로 갈렸다 — 한 정의만 보면 순위가 뒤집힌다.

## 해석 주의사항 (결론 금지의 이유)

1. **튜닝 1회, 결정적 탐색.** 반복·분산이 없다. 평가 횟수 차이 몇 회가 의미 있는지 알 방법이 없다.
2. **파라미터 개수가 다르다(NMPC 6, GSLQR 9, CPID 6).** 나침반 탐색 한 번의 폴링이 2n회를 쓰므로, 같은 예산 120에서 GSLQR은 폴링 약 6.7회, 나머지는 10회다. 학습 곡선에는 제어기 구조와 **파라미터화의 차원**이 섞여 있다.
3. **좌표 순서 의존.** 탐색은 파라미터 목록 순서대로 +s, −s를 평가한다. "k회째에 도달"은 어떤 파라미터가 목록 앞에 있는지에 따라 달라질 수 있다.
4. **사전값 품질이 출발점을 정한다.** 첫 평가 결과·`first_nonfailed`는 설정 파일의 기본 게인 품질을 재는 것이지 튜닝 효율이 아니다.
5. **벌점이 평균을 지배한다.** 시나리오 하나 실패 = 그 시나리오 점수가 RMSE 대신 1000으로 대체 → 평균에 약 +200. 목적함수 값 차이가 실패 개수 차이인지 RMSE 차이인지 표만으론 구분이 안 된다 → `analysis.json`의 평가별 실패 여부, JSONL의 시나리오별 점수를 볼 것.
6. **튜닝 시나리오 5개에서의 값이다.** 본시험 성능이 아니다.
7. **GSLQR 운용점 개수는 설정값이다.** 모든 운용점에서 트림이 물리적으로 존재하는지는 이 도구가 확인하지 않는다(과거 ScheduledLQR이 존재하지 않는 트림점을 격자에 넣어 게인을 오염시킨 사례가 있음).
8. `PARTIAL` 출력의 "최선"은 잘린 구간 안의 최선이다. 최종 결과로 인용하지 않는다.

## 민감도 실행 계획 (`sensitivity_plan.json`)

- 설계: **한 번에 하나(one-at-a-time)** — 최종 가중치(record의 `best_values`)에서 파라미터 하나만 ×0.5 또는 ×2, 나머지는 그대로. 파라미터 간 상호작용은 보지 않는다. 총 실행 수 = Σ 2·n_params (현 설정 2·(6·3+9+6) = 66).
- 시나리오: **튜닝 시나리오**(record의 `scenario_ids`). 본시험 시나리오·난수를 쓰지 않는다. 목적함수 척도가 튜닝과 같아 `baseline.best_objective`와 직접 비교된다.
- ×0.5·×2는 arena_tune의 log₂ 배수 좌표로 정확히 −1·+1이다. 튜닝 중 같은 좌표를 이미 평가했으면 그 값을 `tuning_log_objective`에 **참고로** 붙인다(새로 돌린 값이 아니고, 같은 설정·같은 코드였을 때만 유효). 나침반 탐색이 보폭 2(=±1)로 재시작하므로 상당수가 이미 평가돼 있을 수 있다 — 이는 "이미 탐색된 이웃"이라는 뜻이지 민감도 결론이 아니다.
- 이 도구는 계획만 쓴다. 실행은 `control.arena_tune.parameter_space(...)`의 `apply(values)`로 overrides를 만들어 `Evaluator(...)`에 넘기는 방식이 되며, 별도 작업으로 한다.
